# 決算食堂（仮）

## 1. サービス概要

会社の数字に苦手意識がある外食業界の人が、図解付きの3択クイズでBS（貸借対照表）の基本を学ぶサービスです。
架空の飲食店の取引を題材に、回答後の図解と短い解説で、お金の動きを理解できます。
ログインすると回答履歴が残り、間違えた問題を復習できます。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

2026年に入り、勤務先の公開IR情報をWebで見ても、数字の意味や見方がわからず、「自分の会社の数字なのに、このままではまずい」と感じました。

一方で、業種によってBSの図の形が大きく変わることには面白さを感じました。
文章や数値を眺めるだけでなく、図を見て考え、答えを確かめる形なら、自分も楽しんで学べるのではないかと考えました。

### 2-2. なぜそれが「気になった」のか

自分が働く会社の状況を、数字からも理解したいからです。
わからないままにするのではなく、身近な事例から少しずつ理解し、自分の言葉で説明できるようになりたいと考えています。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

IR情報を開いても、資産・負債・純資産の意味や関係がわからず、読む手が止まってしまいます。

### 3-2. 本当に解決したい課題は何か

- なぜ困るのか：会社の数字を見ても、何を表しているか理解できないからです。
- なぜ理解できないのか：会計用語と、借入や設備購入などの具体的な行動が結び付いていないからです。
- なぜ結び付かないのか：説明を読むだけで終わり、自分で考えて理解を確かめる機会が少ないからです。

→ 本当に解決したい課題：
会社の数字を理解したいのに、学べている手応えがなく、苦手意識から学習が止まってしまうことです。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

外食業界で働き、自社のIRを開いたものの、BSの用語がわからず読むことを諦めてしまう、自分のような会計初心者です。

年齢設定：

- 年齢：40代を起点に想定します。
- 理由：自分に近い一人を想定し、課題を具体化するためです。年代特有の需要は未確認であり、年齢で利用を制限するものではありません。

生活・状況設定：

- 生活・状況：仕事の休憩中や帰宅後に、会社の数字について少しずつ学びたい人です。
- 理由：1回5問に区切り、まとまった時間がなくても取り組めるようにします。

環境設定：

- 環境：主にスマートフォンを使い、専門書や複数のIR資料を広げずに学びたい人です。
- 理由：1画面1問の3択と図解を中心にし、数値の転記や長文入力を不要にします。

### 4-2. 自分とユーザーの距離

- 自分自身。
- 理由：自社の数字を理解したいが、用語や数値だけでは読み進められないという自分の経験が出発点だからです。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- 最初に使う人：自分自身。その後、会計に苦手意識がある外食業界の知人に試用を依頼します。
- 思い出す場面：IRを読んでわからない用語に出会ったときや、会社のお金の仕組みを学びたいときです。
- 現在使っているもの：公開IR情報やWebの解説です。
- このサービスを使う理由：説明を読むだけでなく、回答と解説によって自分の理解を確かめられるためです。

既存の資料を置き換えるのではなく、IRを読む前の基礎学習を補う位置付けです。

自分以外の需要は未確認です。
試用では、解説を読んだ後に変化の理由を説明できるか、もう一問取り組みたいか、復習したいかを確認します。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ

- きっかけ：会社の数字を学びたいときに、知人からの紹介などでサービスを知ります。
- 最初の一歩：登録せずに「基本」のクイズを試します。
- 利用の流れ：難易度を選ぶ→5問に回答する→各問の解説を読む→結果を見る。
- 登録する理由：回答履歴を残し、間違えた問題を後から復習するためです。
- 続ける理由：基本問題で理解を確かめ、応用問題に挑戦したり、間違えた問題を解き直したりするためです。

ゲスト利用の回答は保存しません。履歴を残したい場合は、クイズ開始前にログインします。
毎日の利用を前提にせず、短時間でも一つ理解できることを重視します。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- サービス・教材名：日本商工会議所「簿記初級」のサンプル問題。
- URL：https://www.kentei.ne.jp/bookkeeping/class-s
- できること：簿記の基礎知識を問題形式で確認できます。

公式公開ページで確認しました。
同一形式のアプリではありませんが、会計を問題形式で学ぶ教材として比較対象にしています。

### 5-2. それでも自分が作りたい理由

自分は、資格取得に向けた学習を始める前に、会社の数字に対する苦手意識を減らしたいと考えています。

飲食店の借入や設備購入など、身近な場面とBSの変化を結び付け、スマートフォンで気軽に学べる入口を作りたいです。

既存教材に同様の体験がないとは断定せず、自分が求める学び方との違いを試用を通じて確認します。

### 5-3. 差別化を「体験価値」で表現する

外食業界の会計初心者が、「厨房設備を買うと会社の数字はどう変わるのか」を、短いクイズと図解で理解できる体験です。

問題数や専門性の高さではなく、身近な場面から理解できることを重視します。
この体験が学びやすさにつながるかは、利用者に試してもらい検証します。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：説明を読むだけでなく、自分で答えを考え、間違えた点を確認するようになる。
- 気持ちの変化：「数字は苦手」から「この変化なら説明できる」と感じる。
- 考え方の変化：現金の増減だけで判断せず、資産・負債・純資産の関係を見るようになる。

### 6-2. 価値を一文で表す

このサービスは、会社の数字に苦手意識がある人が、身近な取引のクイズと図解を通じて、BSの基本的な変化を説明できるようになる学習サービスです。

## 7. このアプリで実現すること

### MVPで作る機能

#### ① 図解付き3択クイズ

- 架空の飲食店を題材にします。
- 難易度は「基本・応用」の2段階です。
- 基本は一つの取引、応用は複数の取引を組み合わせた問題を中心にします。
- 初期問題数は基本10問・応用5問を目安にします。
- 選んだ難易度から1回5問をランダムに出題し、同じ回では問題を重複させません。
- 問題の条件と、必要な金額・図を表示します。

必要な理由：
会計用語と具体的な取引を結び付け、自分で考える機会を作るためです。

#### ② 正誤判定・解説・結果表示

- 回答を確定すると、正誤と短い解説を表示します。
- 図解で、取引によって何が増減するかを示します。
- 5問終了後に「5問中何問正解したか」と、各問の結果を表示します。
- 回答後の変更はできず、再挑戦は別の回答として扱います。

必要な理由：
正解を知るだけでなく、なぜその答えになるのかを理解するためです。

#### ③ ユーザー登録・ログイン・回答履歴・復習

- メールアドレスとパスワードで登録・ログインできます。
- ログイン中の回答はユーザーに紐付けて保存します。
- マイページで回答履歴を確認できます。
- 一度でも間違えた問題を、重複を除いて一覧表示し、選んで解き直せます。
- 再回答の結果も保存します。

必要な理由：
苦手だった問題を探し直さず、自分の理解を確かめながら復習するためです。

### 問題データの作成・登録方法

- AIは問題・選択肢・解説の下書き作成に使います。
- 開発者が計算、正解の一意性、解説を確認した問題だけを登録します。
- 利用中にAIで問題を生成する機能は作りません。
- 問題はデータファイルからDBに登録し、MVPでは問題管理画面を作りません。
- 図解は共通の表示形式を使い、問題ごとの描き下ろしを前提にしません。

### MVPで作らないもの

- 実在企業のIR取得・更新
- 株価予想、利益率・ROIによる評価
- 数値を自由入力するBSシミュレーター
- 公開ランキング、ポイント、レベル、連続学習報酬
- 問題のユーザー投稿、コメント、SNS機能
- AIによるリアルタイム生成・チャット
- 3Dキャラクター、音声、複雑なアニメーション
- 全問題を解いた後の自動的な問題追加

### 本リリースで作る機能

MVPの試用結果をもとに、問題文・解説・復習画面を改善します。
追加機能は現時点では確定せず、必要性と開発期間を踏まえて判断します。

## 8. このアプリの懸念点とその対策

### 懸念点①：問題や解説に誤りがある

- 何が問題になりそうか：誤った知識を学ばせてしまうことです。
- なぜそう思うか：AIの下書きには計算ミスや曖昧な条件が含まれる可能性があるためです。
- 対策：公開前に開発者が計算し直し、会計の基本資料と照合します。正解が一つに決まらない問題や、確認できない問題は公開しません。

### 懸念点②：問題が少なく、答えを覚えて終わる

- 何が問題になりそうか：理解せず、選択肢を覚えるだけになることです。
- なぜそう思うか：初期問題数を限定するためです。
- 対策：数字だけを変えるのではなく、用語・取引の変化・複数取引など、考える観点を分けます。試用時には、答えの理由を説明できるかも確認します。

### 懸念点③：簡略化した問題を実際の経営判断に使ってしまう

- 何が問題になりそうか：クイズの正解を、現実の会社の良し悪しと混同することです。
- なぜそう思うか：実際の会計の一部だけを扱うためです。
- 対策：架空の学習用データと明記します。利息・税金・減価償却を考慮しない場合は問題に条件を示し、投資判断や経営の優劣は判定しません。

### 懸念点④：認証と学習履歴の実装で範囲が広がる

- 何が問題になりそうか：アカウント周辺の機能を増やしすぎることです。
- なぜそう思うか：プロフィールやSNSログインなどを追加すると、学習体験以外の実装が増えるためです。
- 対策：学習済みの認証方式を基本にし、プロフィール装飾やSNSログインは作りません。他人の回答履歴を閲覧できないことをテストします。

### 懸念点⑤：問題修正によって過去の履歴と食い違う

- 何が問題になりそうか：問題や正解を変更すると、保存済みの結果の意味が変わることです。
- なぜそう思うか：回答履歴が問題データを参照するためです。
- 対策：回答済みの問題を修正する場合は新版として登録します。旧版は通常出題・復習の対象外にし、履歴には改訂済みと表示して参照を残します。

## 9. 今後の展開・発展の方向性

### 今考えている発展案

- 機能追加の方向性：まず基本・応用のクイズと復習が役立つかを検証します。追加は必要性が確認できたものに限定します。
- UI・体験の改善：スマートフォンでの読みやすさ、選択肢の押しやすさ、解説の理解しやすさを改善します。
- 機能以外の工夫：誤解されやすい問題を見直し、確認できた問題を少しずつ追加します。毎日の追加や定期更新は約束しません。

デザインは、飲食店をイメージした温かい配色と、大きな図・短い文章を中心にします。
1画面1問を基本とし、表形式の情報を詰め込まず、色だけでなく文字や記号でも正誤を伝えます。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：Ruby on Rails、ERB。
- DB：PostgreSQL。
- 画面：HTML・CSSを中心に、必要な箇所のみJavaScriptを使用します。
- 認証：学習済みのRailsの認証方式を基本に、利用するバージョンに合わせて確定します。
- テスト：RSpec。
- デプロイ先：Renderを候補とし、料金と運用条件を確認して確定します。
- 問題登録：データファイルとRailsの登録処理を使用します。
- 外部API：MVPのアプリ内では使用しません。

DBでは、ユーザー・問題・選択肢・挑戦記録・回答を管理します。
問題には難易度、解説、図解用データ、出題対象かどうかを持たせます。

### 10-2. 技術選定の比較検討

| 候補 | 採用／不採用 | 理由 |
| --- | --- | --- |
| Rails＋ERB | 採用予定 | 学習済みの構成で画面・認証・DB処理をまとめて実装するため |
| React＋Rails API | MVPでは不採用 | 構成を分ける学習・実装負担を増やさないため |
| PostgreSQLへの履歴保存 | 採用予定 | ユーザーごとの回答履歴と復習を実現するため |
| ブラウザ内だけの保存 | 不採用 | ログインして別の端末からも履歴を確認できるようにするため |
| 共通形式のHTML・CSS・SVG図解 | 採用予定 | 表示形式を再利用し、問題追加時の制作負担を抑えるため |
| リアルタイムAI生成 | MVPでは不採用 | 正確さの確認、待ち時間、API費用への対応が必要になるため |

- 今回チャレンジしたい点：ランダム出題、ユーザーごとの学習履歴、間違えた問題の復習、スマートフォン向けの図解です。
- 不安な点：同じ回答の二重登録防止、アクセス制御、問題と履歴の整合性です。

### 10-3. キャッチアップ不足の懸念

最初に「1問を表示する→回答する→判定と解説を表示する」を試作します。
その後、5問の出題、認証と回答保存、履歴と復習の順に実装します。

次の点をテストします。

- 選んだ難易度から、重複せずに5問出題されること。
- 正誤をサーバー側で判定すること。
- 二重送信で同じ回答が重複登録されないこと。
- 他人の回答履歴を閲覧できないこと。
- 間違えた問題を選んで復習できること。
- 問題の改訂後も、過去の回答履歴を確認できること。

使用技術の更新状況と利用条件を確認します。
公開サーバーや問題作成に使うAIサービスの料金は、利用前に確認します。
